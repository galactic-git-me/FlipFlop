# Getting Ready service PRD

**Status:** Current sub-PRD; partially implemented  
**Version:** 1.39
**Last reviewed:** 2026-09-30  
**Owner:** Fulfilment and customer experience

## 1. Purpose

Getting Ready owns everything required after a physical build has passed core QA and before it may be dispatched. It produces a reviewed customer package, prepares the workshop USB and machine, gathers shipment evidence, books insurance/courier services, and publishes resulting artifacts to the build portal.

It is not a free-running LLM agent. Deterministic code owns files, allow lists, state, gates, payments, credentials, and publication. The configured LLM drafts structured, reviewable content from supplied evidence.

## 2. Entry conditions

- Ready-to-Ship: create the job at `Built`; attach order/customer at `Sold`.
- Curated-for-you and Made-by-you: create/attach at successful payment; hardware-dependent work waits until `Built` and QA data exists.
- Indirect orders: create against the build/order even when no customer account is linked.

At a marketplace sale, an existing Ready-to-Ship job remains attached to the pre-sale build. Email detection, eBay reconciliation, and manual eBay order sync also idempotently backfill a missing build-scoped job for legacy/exception records under the build-then-job lock order. This fallback never creates a customer or links an account from marketplace buyer email; the printed private claim flow remains the portal-access path.

The Dispatch Centre Getting Ready list includes Ready-to-Ship builds with an existing preparation job while they are `Built` or `Listed`, so measured performance and draft content can be reviewed before listing or sale. `mark-built` accepts only an in-progress or already-built build, serializes on the physical build row, and cannot rewind a Listed or Sold build. Courier booking, insurance, dispatch evidence and handover remain restricted to sold builds. Pre-sale manifest generation is review-only; the customer ZIP and workshop software installer download are held until the sale and customer software choices are recorded. At sale, the existing job and pre-sale orchestration Build row are linked to the customer/order; physical component specifications and pre-sale evidence remain attached, and no duplicate orchestration row is created.

## 3. Customer software Playbook

The target is a recommended set of approved software packages and a plain-English reason for each Playbook cell. The eight canonical use-case Playbooks hold reviewed fallback defaults. Curated matrix cells can carry their own reviewed app list and rationale in the Curated Catalogue admin page; the admin validates package IDs against the installer allow-list. Curated-for-you checkout resolves the selected definition ID (customer type × budget tier), shows the cell recommendation before payment, and snapshots the curated cell ID, cell context, customer selection and rationale onto the order for Getting Ready. Made-by-you now asks customers to declare Budget, Mid-range or High-end in Studio; it resolves the corresponding customer-type × tier software profile, falling back to the use-case profile when that cell has no authored override. The tier travels with shared build links, cart items, payment-intent metadata, the private checkout snapshot, order confirmation and webhook recovery. It is a declared Playbook target, not inferred from the eventual component total. Ready-to-Ship assigns a curated cell when an admin creates the build; the assignment and recommendation follow the build through its pre-sale job, listing and order portal. Legacy Ready-to-Ship builds can be assigned before package generation. Cells without an authored profile inherit the use-case default. Schema migration and runtime verification remain outstanding. The customer sees:

Ready-to-Ship checkout requires a delivery address and a separate billing address, prefilled from delivery when the customer selects “same as delivery.” Both are stored on the reserved product before payment, then copied onto the paid order and linked build. Made-to-order checkout likewise collects both addresses before payment; it stores them in a private payment-intent snapshot, outside Stripe metadata, and transfers them to the order on confirmation or webhook recovery. The temporary snapshots expire after 30 days and are purged opportunistically when a later payment intent is created. An order-linked build shell and Getting Ready portal record are created idempotently at sale; workshop detail and benchmark evidence are added later. Dispatch requires a linked physical build and delivery snapshot before courier booking.

- recommended applications for their use;
- an indicative time saved by FlipFlop preparing them;
- confirmation that FlipFlop's software selection and installation service is included with the build at no extra charge (any paid third-party licence is identified separately before purchase);
- controls to add/remove allowed applications;
- licence and account requirements;
- a lock notice before Components Ordered.

Selections remain editable until `Components Ordered`. For Ready-to-Ship orders, selection remains open until physical dispatch, including after package review. Re-submitting the same submitted set is idempotent regardless of ordering and preserves the approved package. On first submission or a genuinely changed set, the old package is retired from the active artifact index, its review/storage pointers are cleared, its version is retained for monotonic package versioning, and the checklist and build evidence reopen for manifest regeneration and admin review. The old customer/workshop ZIP remains private and is no longer downloadable from active portal or admin package routes. The service accepts only reviewed package identifiers. Saving a changed list invalidates any draft manifest so its installer plan cannot become stale. Manifest generation snapshots the build identity/order/status, exact component specification, benchmark/performance evidence, Playbook assignment and recorded delivery date, as well as the linked job's software selections and paid AI scope, before the model call. It then locks the build before the job through the shared fresh-row helper, rechecks both snapshots—including that a job was not created during generation—rejects stale output, and merges into the latest evidence object so concurrent unrelated evidence is not overwritten. Package approval, checklist updates, dispatch evidence uploads and reviews, and physical dispatch use the same build-then-job lock order to prevent deadlocks and stale handover checks. PostgreSQL concurrency verification is specified in GR-091 and remains unrun pending approval of the platform test plan. If the generation request resolves a database-authored Curated cell profile, it also reloads and locks the parent Playbook and Curated segment before persistence, rejecting a draft if either profile changed. Admin cell-profile upserts lock the parent Playbook before editing the cell, serializing them against this final check. For direct customer orders, package approval waits until the customer submits their choices. For an indirect sale without a linked FlipFlop order, package review requires a separate explicit admin confirmation that the Playbook defaults are suitable; the actor and decision are recorded with the job. Initial package automation uses WinGet. Machine-scope scripts never auto-accept package EULAs; a user-scope app runs in the customer's visible Windows session without the source/package agreement acceptance flags or `--disable-interactivity`, allowing the customer to review and decide any required agreement themselves. The Getting Started guide explains the prompt and that declining a required agreement prevents that app from installing.

For direct made-to-order orders, owner-authenticated cancellation is available only before the order reaches `Components Ordered`. The request pauses sourcing before a full Stripe refund is attempted; retries use a stable provider idempotency key, and a delayed or failed refund remains visible for retry/reconciliation. The admin sourcing milestone and customer cancellation serialize on the same order row. Ready-to-Ship stock has already passed this procurement gate before listing, and indirect-channel cancellations stay with the relevant marketplace or support process. The GettingStartedJob Alembic migration is authored but unapplied; migration and runtime verification remain outstanding.

Admin create/update and proposal approval validate package IDs against the installer allow-list. Checkout displays every approved app, checks the recommended set by default, accepts the customer's add/remove choices, and validates those choices server-side before creating the payment intent. An omitted selection before first submission means “use the recommendation”; an explicit empty list means “install no optional apps” and is preserved through payment metadata, confirmation/webhook recovery, and the Getting Ready job. An omitted field in a later Ready-to-Ship checkout-options update preserves the current PaymentIntent selection. Software selection and installation are included with the PC at no extra charge; third-party licence costs, if introduced, require clear separate disclosure and customer agreement before payment. The selected package IDs and declared budget tier are carried in payment metadata; the server-resolved software profile and selected IDs are also saved in the private checkout snapshot for confirmation and webhook recovery. The seeded defaults cover gaming, student, office, content creation, AI workstation, software development, and family/home profiles; unknown Playbook names receive a small general-purpose set. Curated checkout uses the authored cell profile or the use-case fallback. Made-by-you uses the declared customer-type × tier profile or that same fallback; legacy non-Studio custom configurations use the canonical use-case profile. The time-saving value is indicative, not measured or guaranteed. The GettingStartedJob Alembic migration is authored but unapplied; runtime verification remains outstanding.

## 4. Optional AI services

Paid options are separate line items with explicit consent and eligibility. The initial assistant offer proposes five human-reviewed starter automations: cited research briefs, inbox triage without sending, meeting action drafts, approved-folder file finding, and idea-to-project plans. Other offers cover a personal assistant with a second-brain memory workspace, and a local language model with tools. Each option defines:

- customer benefit and included automations;
- data and account access required;
- supported hardware/software;
- setup boundary and ongoing-support boundary;
- price and refund treatment;
- removal/recovery instructions.

Local GPU services default to 12 GB VRAM minimum unless a reviewed profile supports less. The service never accepts or stores customer secrets in generated documents or logs.

The admin Settings → Getting Ready page can set a one-off price and explicitly enable each reviewed offer; all begin disabled and unpriced. Enabling sales also requires an administrator to attest that the included scope, model/application licensing, account and data needs, recurring costs, support boundary and cancellation/refund terms have been reviewed. The authenticated owner portal displays configured offers and uses a server-priced Stripe Payment Element. The server persists one PaymentIntent per offer/order and attaches a price/scope snapshot to the GettingStartedJob only after the signed Stripe webhook confirms the exact customer, order, offer and amount. Customers can cancel unpaid attempts only after Stripe confirms cancellation; succeeded or processing payments cannot be cancelled. Confirmed cancellations can be retried with a new intent, and abandoned pending payments block final package approval until reconciled. A confirmed purchase invalidates any draft manifest/package so it must be regenerated with the paid scope. Local model setup requires explicit GPU VRAM benchmark evidence of at least 12 GB; absent evidence is ineligible, and VRAM is never inferred from a GPU name. For Made-by-you and Curated-for-you orders, offers become purchasable only after Components Ordered; Ready-to-Ship hardware is already confirmed. Paid AI setup blocks courier booking and dispatch until the operator records completion, and cannot be marked not required. These paths are implemented in source; migration and runtime/payment-provider verification remain outstanding.

## 5. Inputs

- exact build name, component specification, part identifiers and available condition details; the LLM does not receive the customer address, email, order number, build serial, Windows product key, or guest/account token;
- selected Playbook version/cell and recommendation explanation;
- actual benchmark and QA results;
- customer software selections and paid AI services;
- motherboard/RGB/controller identifiers when present in the component specification;
- approved driver/firmware evidence;
- approved component manual cache;
- current generic Getting Started guide uploaded in admin Settings as UTF-8 Markdown or text (maximum 1 MB); configured, legacy request-supplied and generated-intro fallback content use one normalization rule, and build evidence records the selected source and SHA-256 of the exact normalized UTF-8 text snapshotted for package assembly. Package assembly rechecks that checksum before ZIP creation. The guide stays outside the LLM prompt;
- warranty start date and the public support base URL; customer-specific portal URLs and delivery addresses are assembled or stored outside the LLM prompt.

## 6. Generated package

The final versioned ZIP contains:

1. Build plaque artwork/data, rendered as a branded landscape A5 PDF with its source JSON.
2. Exact build specification as a readable PDF and machine-readable JSON.
3. Actual benchmark results as a readable PDF and machine-readable JSON, plus a plain-English interpretation where it is present in the reviewed benchmark data.
4. Current generic Getting Started guide plus build-specific notes.
5. Workshop setup bundle and reviewed master script.
6. Approved drivers, utilities, firmware instructions, and RGB tooling.
7. Component instruction manuals, copied from the central cache where already available.
8. Static HTML upgrade timeline grounded in compatibility and headroom.
9. Portal manifest and checksums.
10. Print-ready personalized portal/QR leaflet.

When the order contains paid AI setup services, the workshop folder additionally contains `AI/paid-ai-setup-runbook.md`, generated only from supported webhook-confirmed purchases. It gives the operator the offer-specific setup boundaries and completion record needed for the paid scope. It is not an installer: no AI application/model is downloaded or executed automatically. The customer and operator must settle the exact assistant/model, accounts, permissions and data location first; the local-model path requires measured GPU VRAM evidence of at least 12 GB. Pending, duplicate, renamed or unknown offers block package assembly rather than being represented as paid.

Every artifact stores source data version, generated-at time, review status, checksum, and publication status. Regeneration creates a new version and never silently alters the package already shipped with an order.

The admin Settings → Getting Ready page maintains a central cache of manufacturer component manuals. An administrator supplies the exact model key, source URL, PDF and an explicit confirmation that the URL is the manufacturer's official support source. Manifest generation matches the complete normalized key by equality against a build component's explicit identity field; it does not search descriptions or accept family-level/substring matches. Package approval rechecks that the cache entry remains active, still matches the component and retains the reviewed checksum before copying the PDF into the ZIP. Dispatch Centre accepts an administrator-reviewed HTTPS research bundle with a component that matches the exact build, topic, publisher, title, access date and claim; the operator attests to each source before generation. For manual research, it checks the active central manual library first by exact normalized identity and displays a cache hit without making an external search request; the hit is not itself approval or ZIP inclusion, which remain subject to exact identity, active-status and checksum revalidation. When no exact cache match exists, it also offers admin-triggered DuckDuckGo HTML search suggestions for an exact build component and selected topic. For manual results, Dispatch Centre can upload a manually downloaded and inspected PDF into the shared cache after the administrator separately confirms the exact model and official HTTPS source; the server never fetches the suggested URL. Changing the component identity or topic clears displayed candidates and cache matches and invalidates any in-flight response or error from the earlier query. Removing a research row also invalidates indexed results and outstanding requests before remaining rows shift. Search results are untrusted, ephemeral candidates containing only title, URL and host: no result page or file is fetched, the search date is not represented as the source access date, nothing is saved or approved automatically, and the admin must inspect the source, record the actual access date, write the supported claim and explicitly attest before generation. The draft starts with a blank access date so the search timestamp cannot be mistaken for the source access date. Approved entries are snapshotted with reviewer identity/time, then used as evidence for LLM drafting, never as permission to fetch or install anything. Runtime validation binds every returned driver/manual reference to an exact model in the persisted build specification, accepts returned URLs only from its approved source records, copies titles/access dates from those records, and forces administrator approval to remain required. LLM-suggested manuals remain in a separate research-review index and are never downloaded automatically. If model output omits an exact build model, manifest validation adds a needs_research manual row and a driver/firmware review row for that model; it carries matching exact, administrator-reviewed sources into those rows when present, while retaining review-required status. Repeated identical parts share one model-level row. This prevents incomplete model output from making a component disappear from dispatch review. Dispatch Centre requires the administrator to complete the component-manual review action with an audit note before package approval; both that action and package approval compare saved manual rows with the current exact build models and representative component IDs, rejecting partial, mismatched or stale manifests. The required action blocks courier and dispatch readiness and is reset whenever a new manifest is generated. If no official manual is available, the note records that outcome instead of silently treating the lookup as complete. Automated manual retrieval and driver/firmware binary caching remain unimplemented.

Driver and firmware review is a separate required action from installing updates. Before the operator marks driver setup complete, Dispatch Centre requires a completed review action whose generated list covers every distinct exact component model and representative component ID in the current build. The operator records a structured outcome for each model, including whether an update was installed or none applies, the explanation, any exact approved source, reviewer and timestamp. An installed update must reference an administrator-approved source for that exact model. Regenerating the manifest resets both the review and installation actions and retires the prior reviewed packages from active customer/workshop download routes.

## 7. Workshop USB and machine setup

The package includes a Windows Setup answer file for en-GB and Microsoft Audit Mode, plus a separate WinPE deployment script. The answer file deliberately contains no target disk, partition instructions, product key, local account, or automated acceptance of licence terms. Before package approval and booting WinPE, the technician records the exact new-build drive model and serial in Dispatch Centre. Package approval requires that current record and embeds the identity into `Deploy-Windows11-Pro.ps1`; the script accepts the official English International media root but no caller-supplied target identity. A missing target makes the generated script fail closed, and the script also refuses to run more than 30 days after the recorded inspection even if the USB was generated earlier. Changing the recorded target after review retires the old archives from active access and requires package regeneration and review. It lists every disk, rejects missing/duplicate identity matches and boot/system/removable targets, checks UEFI mode and required tools, and verifies that the selected image metadata reports exactly Windows 11 Pro and en-GB. It requires the operator to re-enter the exact serial and type two different approval phrases before clearing only the matched disk. It then creates UEFI/GPT partitions, applies the Pro image, stages the answer file for Audit Mode and writes a build-bound installation report. The build name is passed into generated PowerShell as encoded data, not executable source. It never receives a Windows key or customer data. A read-only collector subsequently records the installed edition/locale and actual system-drive model/serial; the API will not accept deployment completion unless those values match the pre-install record. Windows Setup leaves customer account creation to first-run OOBE; the build package creates no technician/customer password and makes no unsupported local-only sign-in claim. Microsoft documents Audit Mode for adding applications/drivers before shipping and `Sysprep /oobe /shutdown` to present customer OOBE on next power-on. The package includes a separate `prepare-customer-oobe.ps1` that only runs from the built-in Audit Mode Administrator, checks the completed setup report and Windows 11 Pro/en-GB, and requires a typed `PREPARE-FOR-CUSTOMER` confirmation before running Sysprep.

The master PowerShell entry point checks for Windows 11 Pro and en-GB system locale, requires an elevated administrator and explicit `RUN` confirmation, installs only the saved allow-listed WinGet selections with explicit machine scope, installs Rainmeter with machine scope, places the centrally templated FlipFlop skin in the shared Rainmeter directory, creates a shared Windows Startup shortcut so the skin activates for the customer's first profile after OOBE, creates the build portal desktop shortcut where a portal URL exists, and writes a status report. User-scope choices such as Discord are excluded from the Audit Mode installer and scheduled from the shared Startup folder to install in the signing-in profile; their deferred state is disclosed in the customer guide. If a machine-scope WinGet package cannot install, setup fails rather than installing it into the temporary workshop profile. If the WinGet package cannot install Rainmeter machine-wide, setup fails instead of leaving the theme in that profile. The package does not bundle third-party installers or automate disk partitioning, firmware updates, RGB hardware, or paid AI installation.

The supported setup sequence follows Microsoft's [WinPE PowerShell instructions](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/winpe-adding-powershell-support-to-windows-pe?view=windows-11), [optional component reference](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/winpe-add-packages--optional-components-reference?view=windows-10), [Windows Setup answer-file process](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/automate-windows-setup?view=windows-11), and [Audit Mode to customer OOBE process](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/boot-windows-to-audit-mode-or-oobe?view=windows-11). The workshop WinPE image must include the required WMI, NetFX, Scripting, PowerShell and StorageWMI components. The answer file must be validated against the exact Windows 11 Pro English International installation media with Windows System Image Manager before operational rollout; the destructive installer also needs supervised hardware acceptance.

The setup has two explicit stages:

- deployment stage: the technician records the exact intended drive before starting Setup, then runs the WinPE installer with official media and that expected model/serial. The script shows every disk and requires two typed confirmations before erasing the uniquely matched target. The answer file selects en-GB and Audit Mode but specifies no disk, partition or product key. A post-install read-only report must match the pre-recorded model and serial;
- post-install stage: selected apps, Rainmeter theme and portal shortcut are included in the master script; licence application, drivers, updates, paid AI setup, and motherboard-specific ARGB profiles remain operator-managed. No reviewed RGB profiles are currently available, so the checklist must mark RGB as not configured until an exact supported controller profile is approved.

RGB profiles are not portable files that can safely be copied between motherboard brands. The official [ASUS Aura developer materials](https://www.asus.com/campaign/aura/us/AURA-ready.php), [MSI Mystic Light SDK materials](https://www.msi.com/Landing/mystic-light-rgb-gaming-pc/download), and [GIGABYTE RGB Fusion SDK materials](https://www.gigabyte.com/mb/rgb/sdk) describe separate control surfaces and supported-device ecosystems. Any future cross-vendor FlipFlop look must therefore be authored as a vendor-neutral *desired effect* (for example, colour palette, static/breathing mode, brightness, and intended zones), then translated by a separately reviewed adapter for the exact board/controller and effect capabilities. The adapter must fail closed when hardware, vendor software/API version, zones, or effect support cannot be identified; it must not silently substitute another effect or claim that a profile was applied. Begin with a human-reviewed profile and documented rollback/reset path. Do not bundle vendor SDK binaries or automate controller writes until licensing, distribution rights, vendor support, and supervised hardware acceptance are established. RGB remains a blocking review item when an approved profile was selected; otherwise the operator may record it as not configured.

Research basis: [ASUS Aura SDK](https://www.asus.com/campaign/aura/us/SDK.php), [MSI Mystic Light SDK](https://www.msi.com/Landing/mystic-light-rgb-gaming-pc/download), and [GIGABYTE RGB Fusion SDK](https://www.gigabyte.com/mb/rgb/sdk), reviewed 2026-09-30. This establishes separate vendor APIs; it does not establish that any specific board, controller, peripheral, or lighting effect is supported by a proposed FlipFlop adapter.

Safety requirements:

- show target disks and require operator confirmation before any destructive action;
- refuse ambiguous/multiple target selections;
- never send a Windows key, password, token, or API credential to the LLM. A Windows Pro key stays encrypted in its order-owned OS component and out of the workshop ZIP. After package approval, an authenticated admin may explicitly download a one-build helper generated in memory from that assigned licence. The response is private/no-store, the key is excluded from the package/customer document index and audit trail, the helper requires a second typed confirmation, and successful use removes it from the USB folder. The legacy Welcome Guide endpoints also require the order owner's customer JWT or a scoped guest portal token; guest tokens cannot regenerate documents. Legacy guide versions are regenerated before serving, and new guides do not print product keys;
- scripts are generated from deterministic templates and approved data, then reviewed; the machine evidence collector is read-only and never handles licence keys or account passwords;
- driver, BIOS, firmware and RGB actions use manufacturer evidence and human approval;
- log every step and support safe retry/resume;
- do not create or retain a technician/customer password. Customer first-use account setup remains in Windows OOBE. Do not claim that hiding online-account screens by itself guarantees a local-account path; any unattended OOBE changes must be checked against the exact Windows image/build and supported Microsoft answer-file documentation before use. Never use an undocumented OOBE bypass;
- automated disk deployment is allowed only through the WinPE script, which binds the target to the recorded model/serial immediately before erasure, displays model/serial/capacity and all competing disks, requires serial re-entry and two typed confirmations, and stops on ambiguity. A numeric unattended-setup DiskID alone is not a durable hardware identity. The answer file itself remains non-destructive.

## 8. Admin experience

`Dispatch Centre → Getting Ready` displays one row per build and the state of its Getting Ready actions. The standalone machine-scope software script is generated on demand from the exact saved selection used by the workshop ZIP. Its authenticated, private download endpoint requires a sold build, submitted customer choices or explicitly accepted indirect-channel defaults, and a reviewed package; the queue response does not contain script contents. Made-to-order selections lock when components are ordered. Ready-to-Ship selections remain editable until dispatch; changing them invalidates the reviewed package, so it must be regenerated and reviewed before the current software script or ZIP can be used.

- source data complete;
- customer selections locked;
- content manifest generated;
- artifacts generated and reviewed;
- USB written/verified;
- machine setup run;
- Windows activation checked where applicable;
- Windows 11 Pro en-GB deployment recorded complete with structured edition, locale, target-drive model and serial, installation method, explicit target-drive confirmation, and an operator note. This is an audit record, not an automated installer or proof sourced directly from the machine;
- drivers/updates complete;
- AI services complete where purchased; with no paid service recorded this action is not required, while a paid service keeps it blocking until the operator records completion. Dispatch Centre asks the operator to confirm the customer approved the exact assistant/model and account/data permissions before accepting completion; the API requires this confirmation flag and stores it with the operator audit note;
- RGB/theme applied;
- QA/benchmark recheck passed;
- portal published;
- leaflet printed;
- working-build photo captured;
- contents-before-packing photo captured;
- sealed-parcel photo captured.

Each action has `not_ready`, `ready`, `in_progress`, `blocked`, `needs_review`, `complete`, or `failed`, with actor, timestamp, evidence, and error. Shipment evidence records the authenticated administrator ID and display name, upload time, category, original filename, content type, byte size and SHA-256 alongside a private storage key. Working-build evidence accepts JPEG, PNG, WebP, MP4, MOV or WebM; contents-before-packing and sealed-parcel evidence require still images. A database failure before commit rolls back and removes the private file. If the connection fails during commit and its outcome is uncertain, the file is retained and an error is logged so a possibly committed record cannot point to deleted bytes; that artifact requires reconciliation. Upload alone is never sufficient: an administrator must inspect and approve each working-build, contents-before-packing, and sealed-parcel artifact with an audit note. Review rechecks the file checksum. A rejected or unreviewed artifact cannot satisfy the insurance or dispatch evidence gates.

Only RGB personalization and AI setup with no paid purchase may be marked `not_required`. Paid AI remains blocking until completed with the customer's scope approval. Required software, Windows installation/activation, driver review, QA, portal, leaflet, package, photo and dispatch actions cannot be waived. The checklist API enforces this rule independently of the admin screen, and the same waiver-aware predicate protects both paid courier booking and physical dispatch, including records containing an invalid legacy waiver.

## 9. Delivery and insurance tab

The Delivery and Insurance workflow is sequential: finish all non-photo Getting Ready actions, quote eligible Parcel2Go services with its optional `Signature` extra requested, explicitly select and pay for the signed-for courier, then upload the required pre-shipment photos, obtain a fresh insurance quote and explicitly create the policy, and finally confirm physical handover. Parcel2Go documents Signature as an optional extra available only on eligible services; the quote must return that extra selected for the service to be offered. The same `Signature` extra is sent in the create-order `Upsells` list. Courier booking and insurance are separate charged admin actions. Courier booking requires a distinct live-purchase confirmation in the authenticated API request; the API re-fetches the selected service and requires its GBP amount to match the displayed confirmation to the penny. It then creates an unpaid provider order and compares that returned total to the confirmed quote before any payment call; missing or changed totals remain unpaid and require administrator reconciliation. The chosen service, signature-extra evidence, provider total, confirmed amount, admin and timestamp are recorded. Insurance and dispatch both require the recorded signature extra. Insurance creation applies the same exact-penny check to the fresh premium before calling the insurer. Reconciliation also compares premium and insured value to the penny, including idempotent checks against an already-linked policy. Uncertain outcomes remain locked for provider reconciliation. Secursus says the tracking number is needed to insure a parcel (or cover must be arranged by the end of the consignment day), so the booking-first sequence supplies it before policy creation. Its current UK guidance requires new, resistant double packaging inside a rigid outer box, adequate cushioning, a package that does not reveal the contents by touch, no package information revealing the item/value or company/site, contents-and-package photos before shipment, adult/direct signature, and carrier collection or handover at an official carrier depot/branch. Parcel shops/lockers require written approval. The insurer specifically requires pre-approval for computer screens, and its cover for returned goods is limited by the original policy period/terms; arrange separate written approval/cover for any return shipment. Our workflow also retains a working-build photo as condition evidence. Insurance must be active before physical handover. See Parcel2Go's [Extras API guide](https://www.parcel2go.com/api/docs/articles/extras.html) and [order creation guide](https://www.parcel2go.com/api/docs/articles/orders.html).

The policy-creation response is checked before it can satisfy dispatch: it must contain a usable policy ID, report `production` mode and GBP currency, and its insured value and premium must match the confirmed sale and fresh quote to the penny. A test-mode or mismatched provider-created policy is saved only as a reconciliation reference; it is not linked as dispatch-valid cover. The authenticated Dispatch Centre queue shows an allow-listed provider response summary after reload, and pre-fills reconciliation suggestions while still requiring the operator to check the provider account and confirm the values. Reconciliation binds to that returned policy ID and recorded amount/currency/mode, and still requires production mode and an insured value matching the sale. If the original response has no usable policy ID, the operator cannot attach a manually entered ID to that response; dispatch stays blocked until the provider record is resolved through the supported reconciliation path. Provider error logging excludes raw response bodies and customer fields. Parcel2Go authentication, quote, order-creation and payment failures likewise retain only safe status/reference details: raw response bodies are neither logged, returned to the operator, nor retained in the booking result. Successful booking logs do not include tracking numbers or label/tracking URLs, and the parsed booking result retains only fields needed for dispatch.

Current insurer controls require:

- verified sale value and customer/delivery details;
- confirmed signed-for service;
- FlipFlop's own evidence set: working-build photo or video, contents-before-packing photo, and sealed-parcel photo. The contents and sealed-parcel stills satisfy Secursus's published photo requirement for the goods and package;
- compliant packaging and retained evidence;
- explicit operator confirmations;
- fresh quote reconciliation before live policy creation;
- insurance creation only after courier booking/tracking, checksum-valid admin-approved contents and sealed-package evidence, and explicit operator confirmation of adult/direct signature, new resistant double packaging, a rigid outer box, concealed contents, discreet item/value/company/site presentation, and eligible official carrier collection/drop-off;
- a final registered-policy check before physical dispatch.
- administrator downloads of private shipment evidence resolve strictly within the requested build's private directory, revalidate its recorded byte size and SHA-256 on one opened file handle, then stream from that same handle; cross-build keys and path replacement cannot expose another build's or unreviewed bytes after verification. Missing, malformed, or changed evidence is rejected and must be uploaded again before review/handover.

Live policy creation remains disabled until production account approval and PC-shipment eligibility are confirmed. Courier and insurer purchases are explicit operator actions. Courier attempts are durably marked before provider calls; a saved booking is returned on retry. For ambiguous outcomes on a sold, courier-booked build, an administrator records the provider check and either attaches the existing policy only when both its parcel tracking number and insured value match the build, or permits another attempt only after confirming no active policy exists. New in-flight insurer requests cannot be reconciled for two minutes, and all resolutions are idempotently audited. Current [Secursus UK terms](https://www.secursus.com/en-gb/terms-and-conditions/) require accurate tracking, carrier, territorial scope, eligible business use, packaging and signature conditions; current [UK shipping instructions](https://www.secursus.com/en-gb/prepare-your-package/) prohibit parcel shops/lockers without approval and require double packaging, discretion and pre-shipment photos. Computer screens require insurer packaging validation before shipment. These external terms must be rechecked before enabling a live account or adding monitor shipments.

Parcel2Go's create-order response maps each submitted item ID to a shipment-level `OrderLineId`; persist this separately from the parent `OrderId`, because its tracking webhook identifies the shipment with that line ID. If the response omits the mapping, do not attempt payment; reconcile the unpaid order first. The authenticated callback rejects stale or replayed events, records tracking stages on the linked order/build timeline, and starts the warranty date/reserve once on delivery using a valid, non-future carrier stage timestamp; malformed or future timestamps fall back to webhook receipt time. As a fallback, an email-monitor delivery confirmation for a directly linked Ready-to-Ship build also updates the order and creates the order-scoped reserve, attaching any earlier order warranty cases; marketplace builds without an order remain build-scoped. The fallback uses a timezone-qualified ISO timestamp only when it appears on a line describing delivery and is not in the future; otherwise it uses message-processing time. If the email monitor finds conflicting order ownership for one physical build, it records the event for operator review and creates no reserve until ownership is reconciled. Matched email confirmations create one portal tracking event; repeat confirmations do not duplicate it or its email. Only direct storefront events are marked for customer email, using the durable courier notification worker and its retry state; marketplace and ambiguous events remain portal-visible without off-platform email. Direct orders receive stage emails; attempts are persisted before SMTP and a scheduled worker retries failures even if Parcel2Go does not resend the event. Scheduled retries also handle direct-storefront dispatch emails and case-status/repair-tracking emails with bounded backoff and an admin alert after eight failures. Case emails store the status and tracking snapshot and commit the outbox row with the admin update before attempting delivery. Indirect/manual-build shipments and cases keep the portal event and do not receive off-platform emails. Configure the same webhook secret in the Parcel2Go account and server environment before registering `/api/webhooks/parcel2go`. This callback and its live account configuration still require sandbox/runtime verification.

## 10. Dispatch and notifications

The generic admin order-status editor cannot mark an order completed unless delivery has already been recorded with its actual timestamp. Use a confirmed carrier delivery or the explicit operator shipment-event action with the event occurrence time; the status editor must not manufacture the date that starts the customer's warranty and reserve clock.

Shipment events recorded against a physical build are rejected when its orchestration Build or sold Product already links it to an Order. Operators must attach tracking and delivery events to that order so the portal timeline and the one sale-owned warranty reserve remain consistent; conflicting order ownership is held for reconciliation.

The authenticated operator shipment-event action rejects delivery occurrence times later than the current UTC time. Provider adapters may apply their documented receipt-time fallback before submitting a normalized event; the operator action never silently substitutes a timestamp.

Dispatch is blocked until all shipment-blocking Getting Ready and delivery checks pass. On dispatch:

- status becomes `Dispatched`;
- tracking and courier appear in the build portal;
- direct customers receive the portal/tracking email;
- failed direct-storefront dispatch emails retry with bounded backoff and raise an admin alert after eight attempts;
- failed direct-storefront aftercare case emails retry from a durable status/tracking snapshot with bounded backoff and raise an admin alert after eight attempts;
- indirect channels receive compliant updates through the channel where required;
- courier events update the portal and generate material status emails;
- live-map links are shown only where the courier supplies them.

Courier integrations normalise signed provider callbacks into the shipment-event contract. The core contract is idempotent by the pair of provider and provider event ID, retains the status description, occurrence time, location and approved tracking/live-map links, and drives the private portal timeline. Provider adapters must authenticate callbacks before ingestion. Portal serialization revalidates all persisted event links, including legacy rows, and exposes only bounded credential-free HTTPS URLs. Warranty repair portal summaries, separate return/replacement shipment links and their event timelines apply the same check. Parcel2Go's initial dispatched event also carries its validated credential-free HTTPS tracking link into the portal timeline and direct-customer email; older handover events fall back to that same validated booking link. Unsafe or overlong links are omitted without hiding shipment status history.

Recorded delivery starts the 12-month commercial warranty, schedules warranty-reserve review, and begins aftercare events.

The operational reserve ledger snapshots the sale value, configured reserve percentage, held amount, warranty start and calendar-year expiry. Warranty cases are linked claims whose approved costs reduce the releasable balance. New warranty cases and explicit reserve release serialize on the owning order/build before the reserve lock, so release cannot overlook a case flushed while its claim is still being attached. The expiry worker uses the same owner-then-reserve lock order, skips rows locked by concurrent work, and rechecks status and expiry after locking; it may mark a balance eligible and notify the administrator, but only a confirmed admin action may release it. A case submitted before the delivery record exists remains linked to the sale and is reconciled to its reserve when delivery creates that reserve; an already-resolved case does not become open again. Open claims block release. The customer portal shows repair-case milestones (review, approval, customer return, inspection, repair/parts, replacement, and outcome), synchronized from admin claim updates. Admins can record the carrier, tracking ID and credential-free HTTPS tracking link for a customer-return parcel and for a later outbound repaired/replacement parcel. Each parcel has its own persisted shipment record and event timeline, so the inbound and outbound Parcel2Go OrderLineIds cannot be confused or overwrite one another. The scoped customer case API exposes the customer-safe carrier and timeline fields while provider references and audit details remain admin-only. Direct storefront orders receive a transactional email when the case status or tracking details change, and a retryable email when either tracked parcel is confirmed delivered; case updates use a durable status/tracking snapshot outbox and alert an administrator if the recipient is unavailable or eight send attempts fail. Marketplace/manual-build cases use printed-portal guidance and do not receive off-platform email. Authenticated Parcel2Go events are deduplicated per provider event and attached to the exact shipment leg. A delivered customer-return parcel advances the case to received for inspection; delivery of the outbound parcel does not automatically close the claim. Intermediate scans remain in the matching portal timeline, and other carriers remain manual-link only.

## 11. Personalized portal and leaflet

Marketplace sale emails never create customer accounts, attach existing accounts by email alone, generate passwords, or send portal credentials. The monitor may retain the parsed buyer email on the sold build solely for optional claim matching; eBay/Vinted and other indirect buyers use the private printed QR claim flow.

All generated customer documents and permitted evidence publish to the private build portal. Authenticated customers reach it from My FlipFlop. The build journey shows a customer-safe Getting Ready milestone and last-updated time when a preparation job exists; only an explicit allow-list of progress flags may enter the customer API. A build-specific preview token containing both a physical build ID and its sold order ID resolves through the order portal path, including the order-owned warranty reserve and order-scoped tracking events. A build-only indirect preview uses a build-owned reserve. The portal must not show an unstarted warranty when the sold order already has an active reserve. The full operator checklist, private notes, evidence, actor details and drive serials stay private to Dispatch Centre. Guests/indirect buyers use a single-use claim flow bound to verified order contact information and see the same safe milestone after claiming. The physical leaflet and build sticker carry a QR code to the claim/login entry point, never a public guessable build URL.

The guest claim credential is stored only as a SHA-256 digest, is revocable, expires, is consumed once under a row lock, and exchanges for a 400-day portal session token scoped to one order or manual build. This covers the 12-month warranty period with a short operational buffer when the claim is issued near dispatch; revoking the underlying grant invalidates the session immediately. Guest portal data is read-only except for a narrowly scoped support-case submission capability; it cannot edit the order, software choices, shipment, or documents. Support and warranty cases retain the verified grant ID and attach to the corresponding order/build and reserve. Issuing a newer unclaimed link revokes older unclaimed links for that portal. For indirect-channel builds, an existing claim cannot be reissued after courier booking because that would invalidate the printed QR already prepared for the parcel. New one-time links place the secret in the URL fragment so it is not sent with the initial page request or normal referrer headers; the storefront removes it from browser history before redemption and accepts legacy query links only during migration. Merely opening the link does not redeem it; the buyer must press the portal button so email scanners do not consume the one-time claim. Direct guest claims require a verified order email and deliver the link by email. Indirect marketplace claims may omit buyer email; when supplied it must match the build's recorded email. They are never emailed, and their raw bearer URL is not returned to Dispatch Centre; the private leaflet is the only delivery mechanism. Before courier booking, direct guests and indirect-channel buyers must have a current, unclaimed claim grant and its private leaflet; marking `leaflet_printed` records the exact grant ID, so reissuing a claim requires replacing and rechecking the leaflet before booking. Signed-in direct customers use their account and do not need a guest grant. Manual/marketplace claims cannot be rotated after booking, and direct guest claims cannot be rotated between booking and handover. At physical dispatch, a direct guest order reuses the pre-issued grant and sends the tracking update separately, without rotating the QR link; only a legacy already-booked build missing its grant uses the recovery path that issues a fresh claim with tracking. If SMTP is unavailable or fails, retain the current private QR leaflet for the parcel. Reissue before courier booking when a replacement is needed; the grant is frozen between booking and physical handover so the printed QR stays valid. After dispatch, direct guests may receive a replacement claim at the verified order email. Account customers receive the normal shipment email. eBay, Vinted, marketplace or printed-insert channels do not receive claim links; they use the printed QR leaflet, and marketplace messages or mediated email must not carry a FlipFlop external link unless a current policy review explicitly permits it.

New direct and printed marketplace claim grants default to 400 days (the same as the resulting guest session) so buyers can claim access throughout the 12-month warranty period when the claim is issued near dispatch. Administrators may choose a shorter validity period, but never more than 400 days.

Customers can attach up to twelve private JPEG, PNG, WebP, or PDF evidence files (10 MB each) to an order-scoped support case. Uploads are bound to the authenticated order or the guest token's single claimed portal, stored outside public static directories, checksum-indexed, and downloaded only through owner, guest-token, or administrator authorization. Every download verifies the stored SHA-256 and returns the same bytes that were checked; missing or changed evidence is not served. Responses are private and use `nosniff`. The admin problem queue exposes each attachment for review. This supports delivery-insurance evidence such as parcel photos, shipping label, proof of value, carrier incident record, and non-delivery/damage documentation; it does not itself submit a claim to the courier or insurer.

The deterministic package assembler includes a branded landscape A5 build plaque PDF and its source JSON, plus a print-ready two-sided A5 portal leaflet. Its first page uses the active guest claim grant when one exists, or a sign-in link for an authenticated order portal; the reverse explains the specification, benchmarks, manuals, upgrade path, delivery tracking, getting-started guide, software setup and aftercare. Claim URLs are generated only after admin issuance; the guest leaflet is private and tied to that grant. The reusable Canva layout reference is [FlipFlop customer build portal leaflet](https://canva.link/0mn6ot8v69qivz0); both pages were visually reviewed. The package renderer remains responsible for merging the build name and actual order-specific QR; a static Canva export must not replace it. The dispatch checklist still requires the operator to print and scan-check the leaflet before marking it complete. Leaflet generation does not satisfy that physical action. The administrator reviews the plaque as part of package approval.

After approval, the portal offers a versioned customer-documents ZIP and individual downloads for customer-facing documents in that same ZIP, including the plaque, specification, benchmarks, guide, exact-match component manuals, upgrade path and applicable portal leaflet. Each item is served only after account ownership or the one-build guest token is verified and the source archive SHA-256 matches the reviewed artifact record. Before streaming a newly generated archive marked `customer_safe`, the server also checks that its member names equal the artifact's customer-document allow-list plus `CHECKSUMS.sha256`; a stale or incorrect metadata pointer to the workshop ZIP is rejected. Cached manual PDFs are accepted only from a single safe filename directly under the manual directory; traversal or nested paths are rejected. The separate workshop USB ZIP contains setup scripts and deployment files and is downloadable only by an authenticated administrator from Dispatch Centre. Newly generated customer ZIPs contain no workshop scripts, answer files or private dispatch checklist. Customer downloads of legacy mixed archives are rebuilt in memory from the document allow-list, after verifying the stored archive digest, so deployment does not require waiting for old packages to be regenerated. The internal dispatch checklist is served separately from Dispatch Centre.

Customer and guest portal JSON exposes only the allow-listed preparation status, confirmed customer-facing AI purchase summary, reviewed customer-document index and customer-package metadata. Pending AI purchases, Stripe PaymentIntent IDs/client secrets and payment-worker metadata are excluded. The internal LLM manifest, source records, component driver/manual review rows, operator outcomes, drive serials, and checklist audit data are not returned to customer APIs. Customers receive the reviewed content through the generated customer documents instead.

Package approval writes both ZIP files before the database transaction records their artifact metadata. A database flush failure before COMMIT is attempted triggers rollback and cleanup of both newly generated files. If COMMIT has been attempted but its outcome is uncertain, the files are retained and their build/storage identifiers are logged for reconciliation; deleting them could break a metadata record that did commit. The approval API returns an error in either failure case, and customer access remains governed by the committed reviewed artifact index.

## 12. AI prompt contract

The version 1.7 template lives at `templates/dispatch/getting-ready-package-prompt.md`. The loader requires a declared version matching the active manifest contract plus the System prompt, User prompt and Output contract sections in that order; it reports a typed generation error before making a model call if the template is malformed or stale. It also requires placeholders for every identity, Playbook, spec, benchmark, customer software/paid-scope, warranty, support, approved research/manual and upgrade-policy input, so a future template edit cannot silently omit evidence. Input placeholders are substituted in one pass over template text only; JSON-encoded input containing braces or placeholder-like strings is preserved as data, and unknown template placeholders fail closed. The combined UTF-8 system and rendered-user prompt is limited to 20,000 bytes and is rejected before provider selection when oversized; inputs are never silently truncated, and the API returns HTTP 413 with actionable guidance. The LLM receives the build name, specification, benchmark results, Playbook explanation, customer selections, deterministic app install scopes, approved research bundle and upgrade policy as data. Generic Getting Started guide content stays outside the model prompt and is included as normalized UTF-8 text in the deterministic package assembler; evidence records its selected source and matching checksum, including the generated-intro fallback. The LLM returns JSON validated against strict nested schemas for plaque, customer copy, app-install plan, upgrade items and portal-document names before persistence; unknown nested fields fail closed. The runtime rejects a mismatched build name, binds selected app IDs and timing to the validated allow-list, binds component references to the build specification, and rejects unapproved URLs or altered source metadata. Embedded instructions in research, component, selection or policy fields must not override the system rules. It cannot browse autonomously, execute scripts, choose live downloads, claim unsupported benchmarks, or mark an action complete. Windows deployment is a separate, build-bound WinPE script in the reviewed package; it does not run automatically or through the LLM. Customer account setup remains in OOBE, and no unsupported Microsoft-account bypass is claimed.

## 13. Acceptance criteria

- All three build types create exactly one durable job at the correct lifecycle stage.
- Customer app changes lock at Components Ordered.
- Machine-scope applications install with explicit scope in Audit Mode; user-scope selections are disclosed and scheduled for the customer's Windows profile rather than installed into the workshop account.
- Saving app choices after manifest generation invalidates the draft; package approval for a direct order requires a submitted customer selection.
- Paid AI options enter the job only from verified order line items.
- A reviewed, checksummed ZIP is generated from exact build data.
- A generated WinPE installer is included in the reviewed package. It deploys only the exact Windows 11 Pro image to the uniquely matched model/serial recorded in Dispatch Centre, after serial re-entry and two separate typed approvals. The script is authored but not yet validated against the exact media with Windows SIM or accepted on supervised physical hardware; do not treat deployment as operational until those gates pass.
- Software selected for workshop setup is installed machine-wide with explicit scope; apps whose reviewed installer supports only a user scope are deferred to that Windows profile's first sign-in and disclosed in the customer guide. A scope mismatch must fail safely rather than install into the temporary Audit Mode Administrator profile.
- Drivers/manuals cite approved manufacturer sources and use the cache before fetching.
- Required evidence and insurance/courier gates block dispatch when incomplete.
- Portal documents are private, versioned, and attached to the correct build/customer.
- Guest portal access can download only the reviewed package attached to the grant's single order or manual build.
- Account and claimed-guest portals show the names and categories of submitted software selections with the indicative time-saving estimate and its basis. Unsubmitted defaults are shown as pending, not as chosen; this is a read-only summary and does not expand guest write permissions.
- Account and guest portals expose individual customer-facing files only from the latest reviewed ZIP; internal scripts are excluded from the individual-file index, and the dispatch checklist is absent from the entire customer archive and available only through an admin-authenticated Dispatch Centre route.
- Delivery starts warranty and reserve schedules using the recorded delivery date.
- Failures are retryable and auditable without duplicate purchases or duplicate jobs.
- A repeated shipment booking returns the stored provider booking; uncertain create/pay outcomes block automatic retries and require a recorded administrator reconciliation first.
- Physical courier handover closes build name/component edits and archiving/inventory release, collection-date changes, manifest generation/package approval, Windows licence/software script release, dispatch checklist and evidence edits, new shipment purchases, shipment-booking reconciliation, and insurer-policy reconciliation. Dispatch Centre receives a safe handover flag and disables these controls while preserving evidence downloads and customer portal access. This remains true after delivery and if a stale dispatch status is encountered, based on the persisted delivered timestamp or handover confirmation as well as the dispatch state. Repeated dispatch is idempotent and preserves `delivered` when delivery has already been recorded.
