# Full PRD to go-live implementation plan

**Status:** Execution plan; not a release approval
**Baseline:** 15 October 2026 DEV evidence
**Scope:** FlipFlop API/admin, FlipFlop.shop, FlipFlopXtension, workers, data, operations and external services.

## Outcome and source of truth

The finish line is a public FlipFlop business that supports Ready-to-Ship, Curated-for-you, Made-by-you, Flip Refresh, sales/fulfilment/aftercare, and the complete phased Growth Engine: social content, a curated customer blog, owned audience, offers, paid advertising, analytics and controlled optimisation. Each public promise must have an operable customer route, a safe operator route, and evidence that the two agree. A working code path alone is insufficient.

Use [product document precedence](../product/README.md), the [PRD register](../prd/README.md), [implementation status](../product/implementation-status.md), and the [approved test strategy](../testing/platform-test-strategy.md). Treat the core-commerce and storefront vNext PRDs as current strategic inputs, Getting Ready as the current fulfilment sub-PRD, the [Marketing Engine PRD](../prd/marketing-engine-prd.md) as its initial scope, and the [Growth Engine mega-PRD](../Growth%20Engine/flipflop-growth-engine-mega-prd.md) with its seven phase PRDs as the designed end state. The Growth phase PRDs govern each phase's acceptance and their mega-PRD sections 32–45 govern shared release, consent, approval and financial boundaries. Historical root `PRD.md` and superseded PRDs do not add release requirements when they conflict with current decisions. Record any remaining contradiction or product decision in the canonical document before building it.

This is a **full-scope finish plan**, not permission to call a smaller pilot full PRD compliance. Releasing a narrower pilot is possible only with a separately approved scope and customer claims.

## Execution rules

1. Maintain one traceability ledger: requirement ID/section, current status, implementation location, evidence link, release gate, and responsible repository. Mark each row `unverified`, `failed`, `verified in DEV`, `verified in staging`, or `verified live`; “source exists” is not a test result.
2. Use small, reviewable changes with migrations and rollback notes. Preserve unrelated local work. Commit coherent baselines per repository after review; never mix generated media, runtime state or credentials into Git.
3. Prove deterministic money, compatibility, stock, fulfilment and state decisions with disposable-database and browser tests. LLMs may draft/explain from evidence; they do not approve or calculate commercial decisions.
4. Keep customer offers unpurchasable when required evidence is missing, stale, conflicting or unapproved. Keep existing paid orders bound to their accepted snapshot.
5. Every phase closes with a dated evidence record. External accounts, legal decisions, supplier approvals and physical workshop trials are named dependencies, not silently simulated successes.

## Phase 0 — Make the baseline safe and measurable

**Build:** Inventory and group all uncommitted API/admin/storefront/extension changes. Resolve existing known type/lint/build failures and reconcile migration heads without touching production. Isolate all database test fixtures in an automatically created, disposable PostgreSQL database whose name ends in `_test`; fail closed if the connection points elsewhere. Capture a fresh baseline for API, admin, storefront and extension; add cross-repository schema/contract checks and a requirement ledger. Remove any customer-safe claims that exceed verified behaviour. Reconcile the historic credential exposure recorded in the existing finish plan before pushing affected history.

**Exit evidence:** Reviewed commits or a clearly identified branch set; clean migration graph on a disposable database; repeatable suite results with all failures triaged; green type/lint/build on each deployable app; documented exceptions with owners and dates. No test can delete developer or production rows. The earlier failing suite is either fixed or each remaining failure is an explicit blocker.

## Growth Engine track — full staged implementation

This track starts alongside Phase 1 and runs to the full PRD finish line; it is not covered by a single social-publishing ticket. One `Advertising & Growth` admin area should show the state of each enabled phase. Shared work first: versioned release/capability flags, Owner/Editor/Reviewer/Analyst permissions, immutable revisions, approval records, consent and suppression contracts, approved media with rights/alt text, source and claim provenance, scheduler/outbox/idempotency, connector execution logs, budgets, audit, emergency pause, and observed analytics. The public storefront needs consent-aware event capture and tracked landing routes. Exercise the actual permission boundary on every Growth API route before enabling external actions.

**G1 — Real marketing MVP.** Replace fixture publishing and synthetic metrics with documented provider adapters for each enabled account, beginning with a verified Facebook Page and Instagram Business route where account permissions support them. Show full API, assisted, analytics-only or unavailable capability per connector. Implement OAuth/token health and revocation, approved media/copy variants, new-build promotion and curated-build rotation, calendar, approval, schedule, availability recheck, posting frequency limits, duplicate detection, global/channel/workflow pause, timeout reconciliation, retries and provider confirmation. Add GA4 connection state and consent-aware storefront events; distinguish observed sessions from provider metrics and unattributed traffic. **Gate:** no fixture ID/metric can be reported as live; actual permitted test accounts publish and return confirmed IDs, uncertain outcomes reconcile before retry, no duplicates in acceptance tests, auditable external actions, freshness SLA and admin accessibility gate from the [MVP PRD](../Growth%20Engine/01-marketing-mvp-prd.md).

**G2 — Automated editorial production and customer blog.** Build a scheduled opportunity queue from approved market observations, customer questions, product availability and measured interest. Automatically propose topics, collect dated sources, draft UK-English briefs/articles and approved-media briefs, then validate claim-level evidence, product facts, price/stock freshness, image rights, brand, SEO, accessibility and links. Add editorial review, immutable revision/approval, preview, schedule, CMS publish confirmation, rollback/update/archive and automatic social *draft* creation. Build a storefront blog feed with categories, search/tags, attractive article cards, article pages, related builds/components, canonical URLs, metadata, sitemap/RSS, mobile and accessible reading, and a clear empty/fallback state. Editorial ranking should favour interesting customer education, not only sales copy. **Gate:** ten representative articles pass source, factual, rights, SEO, accessibility, publish and rollback checks, including a real storefront feed and article; stale or unavailable product claims hold publication. The current [editorial PRD](../Growth%20Engine/02-editorial-expansion-prd.md) explicitly requires approval before public article publication. To meet the requested *automatic publication*, define and approve an amended policy for narrowly eligible low-risk article types, source standards, maximum cadence and immediate takedown; run it in shadow mode first. News, unsupported claims, pricing/stock claims, new media and material revisions remain approval-gated until their own evidence and policy allow them. Do not label automatic drafting/scheduling as automatic public publication.

**G3 — Owned audience and newsletter.** Build consent identity, preferences, suppression, double opt-in where policy requires, bounce/complaint/unsubscribe processing and audience previews. Generate weekly customer-interest digests and build/article features from approved content; review the exact audience, copy and links before sends. Add welcome/lifecycle and abandoned-cart workflows only after consent and identity checks. **Gate:** controlled test edition, duplicate-send and suppression tests, provider outage/recovery, inbox rendering and traceable clicks; no assumed consent or causal revenue claim. Follow the [owned-audience PRD](../Growth%20Engine/03-owned-audience-prd.md).

**G4 — Offers and loyalty.** Implement site-wide, personal, abandoned-cart and loyalty offers with a canonical ledger and deterministic checkout checks for eligibility, expiry, stacking, margin, account binding, refunds and reversals. Generated suggestions cannot issue money-equivalent value by themselves. **Gate:** sandbox checkout plus concurrency, duplicate redemption, account isolation and margin tests per the [offers PRD](../Growth%20Engine/04-offers-loyalty-prd.md).

**G5 — Paid acquisition.** Add campaign planning and approved creative/destination selection, spend caps, budget/profitability assessment and spend/performance reconciliation. Enable eBay Promoted Listings, Google and Meta only one connector at a time after exact API permissions and a provider-specific contract are proved; label assisted/export-only paths. Keep organic and paid metrics separate. **Gate:** one provider at a time passes sandbox/fixture, spend-cap, uncertain outcome, partial success, reconciliation and emergency pause tests; no campaign or budget increase without required approval. Follow the [paid-acquisition PRD](../Growth%20Engine/05-paid-acquisition-prd.md).

**G6 — Analytics and learning.** Reconcile sessions, anonymous-to-account transitions where consent permits, campaign touches, orders, refunds and provider spend without double counting. State model, window, freshness and uncertainty on every attribution figure; holdouts are required for incrementality. Surface useful content/product trends and proposals with evidence, sample size and feedback. **Gate:** the [analytics PRD](../Growth%20Engine/06-analytics-learning-prd.md) synthetic cross-channel dataset reconciles, including unattributed sales and refunds; dashboards never turn correlation into proven lift.

**G7 — Controlled automation.** Run recommendations and action policies in shadow mode; enforce scoped tools, cost/token/time limits, confidence, consent, availability, margin and spend before any side effect. Safe automatic actions may create drafts, resize approved assets, stop an invalid scheduled post or pause spend at a hard cap. Public publication, sending, new audiences, meaningful discounts and budget increases require the configured explicit approval unless a separately amended policy has been reviewed and verified for a narrow content class. **Gate:** observation period with zero policy bypass or duplicate side effect, rollback/reconciliation drills, visible action audit and instant global pause per the [optimisation PRD](../Growth%20Engine/07-controlled-optimisation-prd.md).

## Release gate and cutover

1. Freeze an exact commit/version set for API, admin, storefront and extension. Run the full approved test matrix, migrations against disposable data and staging, browser and accessibility journeys, and approved provider sandbox checks. Record commands, results, environment, dates, known failures and evidence per PRD acceptance criterion.
2. Reconcile the implementation register and support knowledge base with what will actually be public. Verify every published cell/offer and every external account/configuration against live evidence just before launch. A missing external provider disables that dependent offer; full-PRD release remains blocked until the required provider path works.
3. Take a restorable production backup and verify the restore procedure. Apply production migrations and deployment only after explicit production approval, with monitoring, rollback owner and customer-support contact available. Perform a minimal authorised live canary of browse → quote → payment → order → operator queue → portal and a separate dispatch/provider canary when real shipment is possible; reconcile any financial/provider side effect.
4. Declare go-live only when all current PRD acceptance criteria and business operations in this plan have evidence. Hold or roll back on wrong totals, unsafe compatibility/condition, duplicate financial action, missing order/portal state, unfulfillable delivery, privacy leakage or broken support/dispatch recovery.

## Dependencies and sequencing

Phase 0 precedes any broad regression or release candidate. Phase 1 supplies the evidence for Phase 2; Phase 2 supplies offers for Phase 3. Phase 4 can proceed in parallel with Phase 1–3 using simulated offers but needs real paid-order snapshots for final acceptance. Phase 5 can proceed in parallel after shared order, media and catalogue contracts settle. Growth G1 starts after Phase 0; G2 builds on its content/connector foundation and can proceed while commerce closes; G3–G7 follow their stated dependencies. Phase 6 legal/account work starts immediately; its final evidence gates release. Do not make a dependency look complete by creating placeholder prices, stock, capacity, benchmark results, supplier facts, publications or performance metrics.

For implementation tracking, break each phase into repository-scoped issues with a PRD section, exact acceptance test, migration/provider dependencies and reviewer. Refresh the live readiness audit first, then order the Phase 1 queue by blockers shared by the most Playbook cells. Review progress weekly by **verified journeys and publishable cells**, not number of files changed.

### Phase 0 — test database isolation started, 15 October 2026

Source inspection confirmed that `flipflop-api/tests/conftest.py` gives many tests isolated in-memory SQLite sessions, but worker suites including `test_autonomous_notifications.py`, `test_demand_playbook_evolution.py`, and `test_recreate_cycle_job.py` import the application-level PostgreSQL engine and perform broad cleanup. That engine previously inherited the developer `DATABASE_URL`.

Added `flipflop-api/scripts/run_isolated_tests.py` to require a local PostgreSQL maintenance connection, create a uniquely named `flipflop_test_<random>_test` database, mark it with a per-run token, apply `alembic upgrade head`, and then run the requested pytest command. It drops only its own database after complete success; failures retain it for diagnosis. The pytest bootstrap now requires this database marker, binds all application/test database URLs to that run, and blocks Python socket traffic except to the local test PostgreSQL endpoint.

**Not yet verified:** the runner and guard have not been executed. The current test strategy prohibits starting the database, migrations or suite before its stated approval boundary is resolved. PostgreSQL connection permissions and full-suite results therefore remain release blockers. Static source review only; no local database or service was contacted and no test data was changed.
